### Part 1 — DebugPicker (plan A5)

Create debug/DebugPicker.java. Goal: once per game tick (not once per render frame — an actionbar readout doesn't need 60Hz, poll via `net.fabricmc.fabric.api.client.event.lifecycle.v1.ClientTickEvents.END_CLIENT_TICK` like DebugKeybinds does, gated on `Engine.isActive`), and ONLY when there's something peekable enabled (`DebugRenderDispatcher.INSTANCE` — you'll need public accessors if they don't exist; `octree()` already exists from phase 3, check whether a similar accessor exists for the capture layer or whether you should just check `CaptureBuffer.INSTANCE.isCapturing() || !CaptureBuffer.INSTANCE.asCapturedList().isEmpty()` directly), find the closest captured-ray-segment or octree-box-edge to the crosshair and show its numeric fields on the actionbar.

Picking approach (world-space, not screen-space, per the plan — simpler, adequate for a debug tool): from `MinecraftClient.getInstance().player` get eye position (`player.getEyePos()` or `player.getCameraPosVec(1.0f)`, check what's actually available) and look direction (`player.getRotationVec(1.0f)`), build a bounded picking segment (eye, eye + lookVec * 64) using debug.math.Segment3 (read its actual method signatures first, do not guess), then for each candidate compute closest distance via Segment3.closestDistanceTo(...) (ray-vs-ray) — for captured rays each CapturedRay's (start,end) is one Segment3; for octree boxes, you'll need each box's 12 edges as 12 Segment3s (you can reuse the same edge-enumeration logic conceptually as GpuLineBuffer.boxEdges, or add a small shared helper — your call, keep it simple, avoid duplicating the 12-edge math if you can factor it cleanly, but don't over-engineer). Keep the closest match under a fixed threshold (e.g. 0.2 blocks) and closest along the ray (smallest distance from eye to the closest point) if multiple candidates qualify. Wrap the whole per-tick scan in `profiler.push("resounding_debug_pick")`/`pop()` (get the profiler via `MinecraftClient.getInstance().getProfiler()`).

For OctreeLayer, you'll likely need a small public accessor exposing its current box list (it's currently a private `List<Box> boxes` field per phase 3 — read the file to confirm) so DebugPicker can iterate it; add the minimal accessor needed, don't restructure OctreeLayer otherwise.
