<result>## Investigation findings: "larger octant envelops smaller one" (Investigation C)

### Verdict: NOT a geometric bounds-overlap bug. The arithmetic in `Branch.getAtLod`/`virtualLodCell`/`neighbor` checks out. The real defects are (1) a debug-label mismatch that makes aggregate nodes masquerade as pure `air`, and (2) a real but bounded non-convex blend formula in `Polarization.groupAdjust`. Neither, on its own, proves the reported 11–32M values are "corrupted" — the engine's own impedance ceiling is 100M.

### 1. Bounds arithmetic in Branch.java — verified correct (high confidence)

`virtualLodCell` (`Branch.java:216-242`) is only ever reached when `lodSize &lt; size` — both earlier branches of `getAtLod` (`Branch.java:196-201`) already return `this` when `size &lt;= lod`. Given that precondition, `maxX = start.getX() + size - lodSize` is strictly `&gt; start.getX()`, so `Math.max(start.getX(), maxX)` always resolves to `maxX`. The "double clamp" at `Branch.java:222-224` therefore collapses to an ordinary single clamp `[start, maxX]` — it is redundant, not buggy.

`FrustumLod.alignOrigin` (`FrustumLod.java:205-211`) computes `leafStart + floorDiv(pos-leafStart, step)*step`. Since octree nodes are self-aligned (`start % size == 0`, enforced by `growOctree`'s recursive `start.add(block.multiply(scale))` construction, `OctreeManager.java:202`) and `lodSize` divides `size` (both powers of two), `leafStart` is already a multiple of `lodSize`. So for any `pos` inside `[start, start+size)`, the aligned origin naturally lands in `[start, start+size-lodSize]` — the clamp never actually fires for legitimately-routed calls. Hand-checked against ray #50's `node=4³` cell (`start≈(-290,-32,-30) region`, `lodSize=4`): origin arithmetic stays inside the parent's own 4-block box. No overlap into a neighboring node's space.

`neighbor()` (`Branch.java:320-356`) walks to a shifted position and only replicates the coarser ancestor's *single scalar* material/impedance trivially (`impedance,impedance,impedance,NaN,null`) — no aggregation, no compounding.

### 2. The real "envelopment" is a labeling bug, not a bounds bug (medium-high confidence)

`Branch.getAtLod` deliberately returns a coarse node directly whenever `size==lod` (`Branch.java:199-201`), *even if that node still has live, heterogeneous `children`* — its javadoc says so explicitly (`Branch.java:190-192`: "that node's baked polar/avg is the LOD aggregate"). Such a node has `material == null` (set at `OctreeManager.java:246` for any heterogeneous branch) — but the debug label comes from `ensureMaterialLabel` (`Branch.java:291-301`), which reads only `world.getBlockState(start)` — the octant's **corner block**, not the aggregate. So a 2³/4³ node that is genuinely heterogeneous (e.g. one wool/ore corner embedded in otherwise-air) gets tagged `material=air` in the KAPTURE log purely because its corner voxel is air, while its baked `mostCommonImpedance`/`leastCommonImpedance` legitimately reflects the denser corner elsewhere in that same small cube. That is exactly the observed pattern: "air" segments with huge, rapidly-swinging `Z` as the polar-alignment weight (`Cast.java:559-573`) sweeps between the two endpoints. Ray #63 line 126 (`run/logs/latest.log` excerpt in the bug report) shows an actual `material=wool` leaf immediately adjacent to the anomalous air segments — strong circumstantial confirmation this is a hand-placed heterogeneous test region, not corruption.

### 3. `groupAdjust` is a real, bounded arithmetic defect (medium confidence)

`Polarization.groupAdjust` (`Polarization.java:80-92`): `g = otherMean*(1-r²) + mostlyMean*√r`. For `r∈(0,1)` these coefficients do **not** sum to ≤1 — `f(r)=1-r²+√r` peaks at `f(0.397)≈1.472`. Since `mostCount ≥ leastCount` always (primary is defined as most-frequent), `gMost` (`Polarization.java:171`) always hits the `r≥1` clamp and equals `meanMost` exactly (no overshoot). Only `gLeast` (`Polarization.java:172`, `r=leastCount/mostCount`) runs the formula, with reachable integer ratios `{1/7, 2/6, 3/5}` giving `f≈{1.357, 1.466, 1.415}`. So `leastCommonImpedance` can be baked up to **~1.47×** either group's real mean — a genuine non-convex-combination bug, confirmed by hand arithmetic. However, `OctreeManager.bakeAggregateDescriptor` (`OctreeManager.java:269-316`) only takes a plain unweighted mean of 8 children (`sumHigh/children.length` etc., line 309-315) — an average can't exceed its max input, so this ~1.47× overshoot doesn't compound through higher LOD levels. It caps around `1.47 × (max real material impedance)`, not enough alone to explain a jump from bedrock's 4.8M to 32.6M.

### 4. The premise itself is unverified (lowers overall confidence in "corruption")

`MaterialResolver.java:26-27`: `MIN_IMPEDANCE=1e2`, `MAX_IMPEDANCE=1e8` (100 million) — the comment even cites "dense stone ~1e7" as a normal physical value. Bedrock's 4,821,547.5 is not documented anywhere as the registry's ceiling; it's just the highest value that happens to appear later in these 4 rays. Values of 11–32M are well inside the engine's designed range. Before treating them as corrupted, the actual baked impedances of whatever blocks occupy these specific coordinates (various wool colors, ores, stone variants) should be checked against the real `MaterialRegistry`, not against bedrock.

### Recommended fix direction (no code written)
- Fix the label pipeline first: when `branch.material == null` (heterogeneous aggregate), report that explicitly in the KAPTURE dump / overlay instead of falling back to `ensureMaterialLabel`'s single-corner block. This alone would likely eliminate the "material=air, Z=millions" illusion and probably the correlated red-marker false positives (Investigation A) too, since they likely key off the same mislabeled data.
- Separately evaluate `groupAdjust`: either make it a true convex blend (coefficients summing to 1) or explicitly document/test the intentional non-convex "adjuster" behavior — it's a real, boundable overshoot worth closing regardless.
- Add real cell-origin bounds and the heterogeneous/`material==null` flag to the KAPTURE log before further debugging — the current log format can't distinguish "true aggregate of a small heterogeneous cell" from "mislabeled coarse cell" without this, which is why this had to be reasoned from code rather than observed directly.
