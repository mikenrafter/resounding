## 1. Sign of the position-derived vector

**Definitive: `octantCenter - incidentPoint`, normalized — pointing inward, from the crossing point toward the cell center.**

Reasoning: the incident point sits on a face of the cell being *entered*, so the ray direction points into the cell. `center - incidentPoint` also points into the cell — same hemisphere — so averaging them is well-conditioned and semantically coherent ("where the ray is headed" blended with "where the mass of this octant is relative to entry"). The two limit cases confirm this sign and *only* this sign:

- **Dead-center entry aimed at the center**: `C - P` is exactly parallel to the ray → blend is a no-op → alignment equals the current pure-angle result. (With the reversed sign `P - C`, this case sums two anti-parallel unit vectors to the zero vector — degenerate exactly where behavior must be unchanged. That kills the reversed sign outright.)
- **Tangent entry**: a ray grazing the cube's silhouette travels nearly parallel to a face, so `C - P` is nearly perpendicular to the ray. The normalized sum is the exact angular bisector, 45° off the ray. If the ray was perfectly pol-aligned (raw alignment 1.0), the blended alignment is cos²45° = **exactly 0.5** — precisely the "~halfway between the two" the product requirement asks for. The geometry produces the requested number with no fudge factor; that is strong evidence this interpretation is right.

Degenerate guard: if `(C - P)` has `lengthSquared() &lt; 1e-12`, or the sum `rayNorm + normalize(C-P)` has `lengthSquared() &lt; 1e-12`, fall back to raw `rayNorm`. (The anti-parallel case can't occur for a genuine entry crossing, but floating-point exit-face hits shouldn't NaN the impedance path.)

public static Vec3d grazeBend(Vec3d ray, Vec3d rayNorm, Vec3d polNorm) {
    double n = polNorm.dotProduct(rayNorm);
    if (n &lt;= 0) return ray;                      // already heading away from solid

    Vec3d tangent = rayNorm.subtract(polNorm.multiply(n));
